# 《聚闪耀 (FlashMeet)》系统详细设计与开发落地指导文档

## 1. 系统架构与全景概览 (System Architecture & Overview)

### 1.1 总体产品矩阵：“一网三端一云”
为了支撑“计算相遇的概率，渲染心动的瞬间”这一宏大愿景，聚闪耀系统采用多租户（Multi-Tenant）高并发架构，整体划分为“一网、三端、一云”：
1. **官网门户 (Official Website)**：聚闪耀的“门面”与获客入口，展示产品使命、核心玩法、应用场景。支持潜在主办方通过扫码一键注册成为平台用户。
2. **大屏展示端 (PC Web)**：聚会现场的“数字中心”。由主办方发布活动后生成的唯一Web链接打开，负责3D视觉呈现（星系签到、动画、游戏画面）以及展示供参会者扫码入场的动态二维码。具备2D/3D优雅降级能力。
3. **用户小程序端 (WeChat MP - User)**：参会者的“数字面具与交互器”。负责扫码签到、参与渐进式游戏、接收实时提醒、与全场进行双盲匹配互动。
4. **主持人控制端 (WeChat MP - Admin)**：主办方的“移动遥控器”。负责聚会信息配置、发布生成大屏链接、现场环节强切（场控）、发起抽奖/游戏。支持副场控(Co-Host)权限转移。
5. **云端服务 (Backend Cloud)**：支持全国范围**多场聚会同时开展**的核心大脑。负责业务逻辑、多租户数据隔离、数据报告生成及基于 WebSocket 的毫秒级跨端消息路由。

### 1.2 技术栈选型（稳定为王）
- **前端体系**：
  - 官网门户：Nuxt.js / Next.js（利于SEO） + TailwindCSS。
  - 大屏展示端：Vue 3 + Vite + TypeScript + Three.js（3D引擎）+ GSAP。**必须包含 CSS3 2D 降级方案，保证在无独显的老旧酒店电脑上也能流畅运行。**
  - 微信小程序（主客双端）：Uni-app + Vue 3（一套代码，权限控制隔离视图）。
- **后端体系**：
  - 核心API与长连接：Node.js (NestJS) 或 Go 语言。构建高并发 WebSocket Server，**必须支持 HTTP 长轮询/短轮询降级（Socket.io 原生支持）**。
  - 数据持久层：MySQL 8.0 或 PostgreSQL（利用 `tenant_id` 或 `event_id` 实现多场聚会数据逻辑隔离）。
  - 高频缓存与消息队列：Redis（处理签到并发、摇一摇积分汇聚、WebSocket 分布式 Pub/Sub）。
- **云基础设施**：腾讯云/阿里云、OSS（图片/视频）、CDN加速静态资源。

## 2. 核心业务流程与交互闭环 (Core Workflows)

### 2.1 官网引流与主持人注册发布流程
1. **扫码注册**：潜在主办方在官网扫码，一键授权注册成为“聚闪耀主持人”。
2. **移动端配置**：主持人在小程序中填写聚会基础信息，配置抽奖池与互动游戏，可添加**副场控 (Co-Host)** 协助。
3. **一键发布**：配置完成后生成全局唯一的 `Event_ID` 和专属的大屏 Web 链接（如 `https://screen.flashmeet.com/e/12345`）。
4. **大屏就绪**：电脑连接大屏打开链接，系统自动检测设备性能，决定加载 WebGL 3D 模式或降级为 2D 模式。大屏主动向后端发起 `JOIN_ROOM` 请求，等待指令。

### 2.2 参会者“扫码 - 渐进式画像 - 上墙”闭环
1. **秒级扫码入场**：参会者扫描大屏二维码，无需繁琐填表，授权微信基础信息后 **1秒上墙**，化作一颗“暗星”飞入大屏星系。
2. **渐进式画像 (Progressive Profiling)**：
   - 入场后，大屏由主持人发起破冰问答游戏（例如：“你是 I 人还是 E 人？”、“你的职能是？”）。
   - 参会者在手机端点击选择，每次选择都会让大屏上的对应“暗星”瞬间点亮专属颜色标签。
   - 通过游戏化的方式，无感且高效地收集用户画像，大幅降低入口流失率。

### 2.3 移动场控、双盲破冰与实时互动
1. **场景强切（主持人动作）**：主持人通过小程序“场控台”自由切换环节（如签到切抽奖）。指令经 WebSocket 路由到大屏。若主控断网，**副场控** 可无缝接管。
2. **双盲隐私与反骚扰破冰**：
   - 开启“CP盲盒匹配”或“标签雷达”后，大屏连线最匹配的陌生人。
   - 手机端收到匹配提示，支持**双盲聊天**（仅限系统预设破冰语）。
   - 只有双方均点击“同意交换名片”，才展示真实微信号。
3. **双端互动（摇一摇）**：参会者疯狂摇动手机，Redis 汇总排名，每 500ms 广播给大屏渲染实时进度。

### 2.4 聚会数据沉淀与长效社交池 (After-Party)
1. **数字成就卡裂变**：活动结束，每位参会者手机端自动生成一张《聚闪耀·数字社交成就卡》，鼓励分享以获取“免单办会特权”（PLG 增长飞轮）。
2. **延时社交沉淀池**：活动结束后 24 小时内，参会者可查看“全场与我标签重合度最高的人（已授权公开）”，提供二次破冰机会。
3. **主办方数据报告**：为管理员生成《聚会复盘报告》（包含签到转化漏斗、互动率等数据分析），支持一键导出。

## 3. 【新增开发视角】核心状态机设计 (Core State Machine)
**（重要：这是开发能否看懂并顺利编码的核心）**

整个聚闪耀系统本质上是一个**“以主持人为驱动，通过服务端广播，强同步大屏和用户手机端状态”的分布式状态机**。

### 3.1 聚会全局状态流转 (Event Status)
每场活动在 Redis 中维护一个当前的 `current_state`，所有的端（大屏、用户、主持人）都必须根据这个状态渲染对应的 UI。
*   `STATUS_STANDBY` (待机)：大屏显示宣传视频或倒计时，用户端显示“活动未开始”。
*   `STATUS_CHECKIN` (签到中)：大屏显示星系签到和二维码，用户端显示渐进式答题器。
*   `STATUS_LOTTERY_READY` (抽奖准备)：大屏显示奖品，用户端显示“看大屏，准备抽奖”。
*   `STATUS_LOTTERY_RUNNING` (抽奖进行中)：大屏滚动头像，用户端锁定不可操作。
*   `STATUS_GAME_SHAKE` (摇一摇游戏)：大屏显示赛车跑道，用户端显示摇一摇手柄。
*   `STATUS_ENDED` (已结束)：大屏显示感谢致辞，用户端生成数字成就卡。

### 3.2 晚入场状态同步机制 (Late-Joiner Sync)
*   **痛点**：用户在抽奖进行中才扫码入场，或者大屏中途刷新，此时如果不做状态同步，两端画面会错乱。
*   **开发方案**：任何一端（大屏或手机）在建立 WebSocket 连接或通过 HTTP 短轮询获取数据时，第一步**必须且仅能**调用 `GET /api/event/{event_id}/current_state` 接口。获取到当前状态（例如正在 `STATUS_GAME_SHAKE`）后，客户端强制跳过前面的签到页面，直接渲染摇一摇手柄。

## 4. 【新增开发视角】核心通信协议与高并发处理 (Communication & Concurrency)

### 4.1 WebSocket 核心事件字典 (Event Dictionary)
为了保证稳定输出，前后端必须严格按照以下事件名进行 Pub/Sub 通信：
*   **`HOST_CHANGE_SCENE` (Client -> Server)**：主持人下发切屏指令，Payload 包含 `target_state`。
*   **`SCENE_UPDATED` (Server -> All Clients)**：服务端广播状态变更。大屏和所有用户手机收到后立刻切换 UI。
*   **`USER_CHECKED_IN` (Server -> Big Screen)**：服务端通知大屏有新用户签到，大屏渲染“暗星”飞入。
*   **`USER_SHAKE_ACTION` (User -> Server)**：用户摇动手机（节流：每 500ms 发送一次，不要每次摇动都发，防止压垮服务器）。
*   **`SHAKE_LEADERBOARD_TICK` (Server -> Big Screen)**：服务端每 500ms 将 Redis 中聚合的摇一摇排行榜下发给大屏渲染。
*   **`LOTTERY_WINNER_ANNOUNCE` (Server -> All Clients)**：公布中奖名单。中奖用户的手机触发震动特效。

### 4.2 抽奖防超卖与幂等性保障 (Idempotency Guarantee)
*   **痛点**：如果主持人因为网络卡顿连点了两下“抽取”，或者黑客通过抓包重放接口，会导致奖品被超发。
*   **开发方案**：后端必须使用 Redis Lua 脚本进行原子操作扣减奖品库存。所有关键接口（如抽奖、签到、发放积分）必须带上 `request_id` 或基于 `user_id + action` 做**幂等性校验**。

## 5. 【新增开发视角】异常边界场景与容灾设计 (Edge Cases & Fault Tolerance)
**（重要：线下活动“绝对不能卡死”，稳定性大于一切技术花活）**

1. **极端弱网环境（如酒店地下二层，几百人挤占基站）**：
   *   **降级策略**：Socket.io 默认开启 `transports: ['polling', 'websocket']`。如果 WebSocket 无法建立或频繁断开，系统静默降级为 HTTP Long Polling。用户完全无感知，虽然延迟会从 50ms 增加到 1s，但保证了抽奖和互动依然能跑通。
2. **主办方设备掉线或没电（主持人手机卡死）**：
   *   **降级策略**：设计 **“副场控 (Co-Host) 机制”**。主场控在开场前可授权 2-3 个核心工作人员为副场控。主场控掉线时，副场控的手机同样拥有切屏和发奖权限。
3. **现场大屏电脑性能极差（无独立显卡的老旧 PC）**：
   *   **降级策略**：大屏端初始化时计算前 10 帧的 FPS。如果低于 15 FPS，自动弹出提示并切换为 `CSS3 2D 粒子模式`（屏蔽所有 Three.js 复杂光影计算）。
4. **用户恶意刷票或作弊（使用模拟器摇一摇）**：
   *   **防刷策略**：前端节流控制；后端对单用户每秒最大的 `USER_SHAKE_ACTION` 数值设定阈值（例如人类极限是 10 次/秒），超过该数值的请求直接丢弃并标记异常。

## 6. 数据库设计优化 (Database Schema V2)

### 6.1 核心表结构 (多租户支持)
*   **`Global_Users` (全局用户表 - 支撑跨场次身份)**：
  *   `user_id` (PK), `wechat_openid`, `global_tags` (JSON), `event_participated_count`.
*   **`Events` (聚会活动表)**：
  *   `event_id` (PK), `host_id` (FK), `co_host_ids` (JSON), `settings` (JSON: 包含UI配置、玩法开关).
*   **`CheckIns` (单场画像)**：
  *   `id` (PK), `event_id` (FK), `user_id` (FK), `local_tags` (JSON), `is_invisible` (隐身模式).
*   **`Assets_Store` (创作者资产表)**：
  *   `asset_id`, `creator_id`, `type`, `price`, `preview_url`.

## 7. 结语与开发落地排期建议
对于研发团队，建议分两步走：
*   **Phase 1 (MVP - 保稳定)**：首月不追求极致的 3D 特效，集中兵力打通**“状态机同步机制”**和**“WebSocket 通信链路”**。跑通“主持人建会 -> 大屏显示 -> 用户扫码签到 -> 主持人切屏抽奖”的主流程，并在各种弱网、断网、刷新环境下进行极端破坏性测试。
*   **Phase 2 (进阶 - 提体验)**：在底层状态机极其稳定的基础上，再叠加 Three.js 3D 粒子系统、CP 盲盒匹配算法和数字成就卡分享逻辑。
