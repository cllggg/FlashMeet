## 1. 系统架构与全景概览 (System Architecture & Overview)

### 1.1 总体产品矩阵："一网三端一云"
为了支撑"计算相遇的概率，渲染心动的瞬间"这一宏大愿景，聚闪耀系统采用多租户（Multi-Tenant）高并发架构，整体划分为"一网、三端、一云"：
1. **官网门户 (Official Website)**：聚闪耀的"门面"与获客入口，展示产品使命、核心玩法、应用场景。支持潜在主办方通过扫码一键注册成为平台用户。
2. **大屏展示端 (PC Web)**：聚会现场的"数字中心"。由主办方发布活动后生成的唯一Web链接打开，负责 3D 视觉呈现（星系签到、动画、游戏画面）以及展示供参会者扫码入场的动态二维码。**v3.0 起完全统一为单一 3D 舞台 `Stage3D.vue`**，不再做 2D 降级（详见 §8.2）。
3. **用户小程序端 (WeChat MP - User)**：参会者的"数字面具与交互器"。**v2.0 起重构为"单一 Live 容器"**——用户从扫码到离开，全程 0 页面跳转。签到、破冰、摇一摇、抽奖、匹配、成就卡等环节，均在同一 `live` 容器内通过 Overlay 切换完成。负责扫码签到、参与渐进式游戏、接收实时提醒、与全场进行双盲匹配互动。
4. **主持人控制端 (WeChat MP - Admin)**：主办方的"移动遥控器"。**v3.1 起重构为"指挥家 (Conductor) 视图 + 智能助手"**——**单列布局**：顶部连接状态与切换入口，中部 Hero 卡（CSS 镜像 + 实时数据 + 智能建议三合一），主操作永远 1-2 个大按钮（100rpx 高、拇指友好），底部 Timeline 展示全流程，AI 助手自动建议下一步。负责聚会信息配置、发布生成大屏链接、现场环节强切（场控）、发起抽奖/游戏。支持副场控(Co-Host)权限转移。
5. **云端服务 (Backend Cloud)**：支持全国范围**多场聚会同时开展**的核心大脑。**v2.0 新增 `HostAssistantService` 智能助手模块**与 `experience_stream` 体验流数据模型。负责业务逻辑、多租户数据隔离、数据报告生成及基于 WebSocket 的毫秒级跨端消息路由。

### 1.2 技术栈选型（稳定为王）
- **前端体系**：
  - 官网门户：Nuxt.js / Next.js（利于SEO） + TailwindCSS。
  - 大屏展示端：Vue 3 + Vite + TypeScript + Three.js（3D引擎）+ GSAP + UnrealBloomPass（后处理）。**v3.0 起只保留 3D 路径**，设备基线 8GB RAM + i8 处理器，移除所有 2D 兜底代码。
  - 微信小程序（主客双端）：Uni-app + Vue 3（一套代码，权限控制隔离视图）。
- **后端体系**：
  - 核心API与长连接：Node.js (NestJS) 或 Go 语言。构建高并发 WebSocket Server，**必须支持 HTTP 长轮询/短轮询降级（Socket.io 原生支持）**。
  - 数据持久层：MySQL 8.0 或 PostgreSQL（利用 `tenant_id` 或 `event_id` 实现多场聚会数据逻辑隔离）。
  - 高频缓存与消息队列：Redis（处理签到并发、摇一摇积分汇聚、WebSocket 分布式 Pub/Sub）。
- **云基础设施**：腾讯云/阿里云、OSS（图片/视频）、CDN加速静态资源。

### 1.3 【v2.0 新增】UX 驱动的架构原则 (UX-Driven Architecture Principles)

> **核心思想**：教程、引导只是止痛药，UX 才是治本。系统架构必须围绕"用户认知流"设计，而不是围绕"功能模块"设计。

**为什么需要这一章**：
在 v1.x 版本中，系统采用"Page-Per-Scene"架构（每个环节一个页面，靠 WS 推送跳转）。实测发现：
- 新用户从扫码到首次互动平均需 3 分钟、经历 3 次跳转；
- 新主持人首场聚会"不知道下一步该干嘛"的发生率高达 80%；
- 用户每场活动页面跳转 5+ 次，每次跳转 = 一次认知重启 = 一次流失风险。

v2.0 重构的根本目标：**通过架构升级，从根本上消除对教程和引导的依赖**。

#### 1.3.1 七大 UX 准则（团队共识）

```
┌──────────────────────────────────────────────────────────────────┐
│  FlashMeet UX Principles (v2.0)                                  │
├──────────────────────────────────────────────────────────────────┤
│  1. 零跳转原则    用户从进入 Live 到离开 Live，最多跳转 0 次     │
│  2. 持续在场感    用户始终能看见：自己是谁、场子有谁、当前在干嘛 │
│  3. 下一步永远可见 ContextBar 永远显示"下一环节 + 倒计时"      │
│  4. 一个屏幕一个主行动  每个屏幕只有 1 个最显眼的按钮            │
│  5. 状态可视化    任何"等待"都要有进度；"失败"要可重试；       │
│                  "成功"要有正向反馈                              │
│  6. 拒绝 Modal    禁止模态弹窗；用 page transition 替代          │
│  7. 引导最小化    不做长篇 onboarding；只对新功能一次性 spotlight│
└──────────────────────────────────────────────────────────────────┘
```

#### 1.3.2 三大架构范式转移

| 维度 | v1.x 范式 | v2.0 范式 |
|---|---|---|
| 页面组织 | Page-Per-Scene（每场景一页） | **Stage Model**（单 Live 容器 + Overlay） |
| 数据状态 | 单一 `current_state` 字段 | **Experience Stream**（current + queue + history） |
| 主持人决策 | 手动点 10 个按钮 | **Conductor + HostAssistant**（智能建议 + 一键执行） |

#### 1.3.3 5 个用户旅程关键时刻（5 Moments of Truth）

任何一场活动，UX 必须在以下 5 个时刻做到极致：

| # | 时刻 | 关键体验要求 | v2.0 衡量指标 |
|---|---|---|---|
| T1 | **到达**（扫码→进 Live） | 1 步完成，无表单困惑 | 扫码到首互动 < 30s |
| T2 | **首次互动** | 0 跳转，MainStage 自动变换 | 跳转次数 = 0 |
| T3 | **峰值参与**（摇一摇/抽奖） | 沉浸感，背景音乐 + 视觉冲击 | 用户停留率 > 90% |
| T4 | **高潮**（开奖/匹配） | 倒计时 + 强反馈（震动/声音） | 高潮环节参与率 > 70% |
| T5 | **离开**（成就卡/分享） | 自动浮出，自然引导 | 7 日回访率 > 30% |

#### 1.3.4 架构落地的"舞台模型"（Stage Model）一览

```
┌─────────────────────────────────────────────────┐
│  Header  [Event]    [在场 23 人]    [我 ⋯]      │  ← 永远在
├─────────────────────────────────────────────────┤
│         ✨ 当前环节：自由交流 ✨                  │  ← StageStatus
│                                                 │
│      [MainStage 动态变换：签到/破冰/摇一摇/     │  ← 单一容器内的演员
│       抽奖/匹配/结束 全部以 Overlay 出现]        │
│                                                 │
├─────────────────────────────────────────────────┤
│  [我:🌟]  [我已就绪]   [⏭ 下一环节 3:00]       │  ← ContextBar 永远在
└─────────────────────────────────────────────────┘
       ↗ 右上角 Drawer：成就 / 聊天 / 社交池
```

## 2. 核心业务流程与交互闭环 (Core Workflows)

### 2.1 官网引流与主持人注册发布流程
1. **扫码注册**：潜在主办方在官网扫码，一键授权注册成为“聚闪耀主持人”。
2. **移动端配置**：主持人在小程序中填写聚会基础信息，配置抽奖池与互动游戏，可添加**副场控 (Co-Host)** 协助。
3. **一键发布**：配置完成后生成全局唯一的 `Event_ID` 和专属的大屏 Web 链接（如 `https://screen.flashmeet.com/e/12345`）。
4. **大屏就绪**：电脑连接大屏打开链接，直接加载 WebGL 3D 舞台 `Stage3D.vue`（不再做设备性能探测与 2D 降级）。大屏主动向后端发起 `JOIN_ROOM` 请求，等待指令。

### 2.2 参会者“扫码 - 渐进式画像 - 上墙”闭环
1. **秒级扫码入场**：参会者扫描大屏二维码，无需繁琐填表，授权微信基础信息后 **1秒上墙**，化作一颗“暗星”飞入大屏星系。**v2.0 起改为：扫码后直接进入 Live 容器，签到流程以 Overlay 形式在容器内完成，无独立 checkin 页**。
2. **渐进式画像 (Progressive Profiling)**：
   - 入场后，大屏由主持人发起破冰问答游戏（例如：“你是 I 人还是 E 人？”、“你的职能是？”）。
   - 参会者在手机端点击选择，每次选择都会让大屏上的对应“暗星”瞬间点亮专属颜色标签。
   - **v2.0 增强**：破冰问题在 Live 容器内以底部滑出卡片 (Bottom Sheet) 形式出现，答完自动收起，不打断用户。
   - 通过游戏化的方式，无感且高效地收集用户画像，大幅降低入口流失率。

### 2.3 移动场控、双盲破冰与实时互动
1. **场景强切（主持人动作）**：**v3.1 起改为"Conductor 视图"——单列布局：顶部连接状态/切换/结束图标按钮，中部 Hero 卡（CSS 镜像替代 iframe 预览，避免跨域和重复 3D 渲染），主操作永远 1-2 个大按钮，底部 Timeline 常驻**。原 dashboard 多按钮场控台废弃。
2. **双盲隐私与反骚扰破冰**：
   - 开启“CP盲盒匹配”或“标签雷达”后，大屏连线最匹配的陌生人。
   - 手机端收到匹配提示，支持**双盲聊天**（仅限系统预设破冰语）。**v2.0 强化：聊天 UI 改造为"破冰语库 + 解锁自由输入"模式，避免广告/骚扰**。
   - 只有双方均点击“同意交换名片”，才展示真实微信号。
3. **双端互动（摇一摇）**：参会者疯狂摇动手机，Redis 汇总排名，每 500ms 广播给大屏渲染实时进度。

### 2.4 聚会数据沉淀与长效社交池 (After-Party)
1. **数字成就卡裂变**：活动结束，每位参会者手机端自动生成一张《聚闪耀·数字社交成就卡》，鼓励分享以获取“免单办会特权”（PLG 增长飞轮）。
2. **延时社交沉淀池**：活动结束后 24 小时内，参会者可查看“全场与我标签重合度最高的人（已授权公开）”，提供二次破冰机会。
3. **主办方数据报告**：为管理员生成《聚会复盘报告》（包含签到转化漏斗、互动率等数据分析），支持一键导出。

## 3. 【新增开发视角】核心状态机设计 (Core State Machine)
**（重要：这是开发能否看懂并顺利编码的核心）**

整个聚闪耀系统本质上是一个**“以主持人为驱动，通过服务端广播，强同步大屏和用户手机端状态”的分布式状态机**。

### 3.1 聚会全局状态流转 (Event Status)
**v2.0 升级：从"单一状态字段"升级为"体验流 (Experience Stream)"**

#### 3.1.1 v1.x 状态机（保留作为底层实现）

每场活动在 Redis 中维护一个当前的 `current_state`，所有的端（大屏、用户、主持人）都必须根据这个状态渲染对应的 UI。
*   `STATUS_STANDBY` (待机)：大屏显示宣传视频或倒计时，用户端显示“活动未开始”。
*   `STATUS_CHECKIN` (签到中)：大屏显示星系签到和二维码，用户端显示渐进式答题器。
*   `STATUS_LOTTERY_READY` (抽奖准备)：大屏显示奖品，用户端显示“看大屏，准备抽奖”。
*   `STATUS_LOTTERY_RUNNING` (抽奖进行中)：大屏滚动头像，用户端锁定不可操作。
*   `STATUS_GAME_SHAKE` (摇一摇游戏)：大屏显示赛车跑道，用户端显示摇一摇手柄。
*   `STATUS_ENDED` (已结束)：大屏显示感谢致辞，用户端生成数字成就卡。

#### 3.1.2 v2.0 体验流（Experience Stream）—— 新的数据模型

> **核心理念**：单场活动不再只是一个"当前状态"，而是一条"体验流"——包含 **当前环节、计划队列、历史回放、AI 建议** 四部分。主持人端能基于此渲染"全剧本时间线"，用户端能基于此渲染"下一环节预览"。

```typescript
// 新数据结构（存于 Redis + MySQL）
interface ExperienceStream {
  // 当前正在进行的环节（最多 1 个 main，可叠加多个 sub-overlay）
  current: StreamNode | null;
  
  // 计划但未开始的环节队列（AI 排序 + 主持人可调）
  queue: StreamNode[];
  
  // 已结束的环节（含指标）
  history: StreamNode[];
  
  // AI 推荐的"下一步建议"（最多 3 个，含一键执行）
  suggestions: ActivitySuggestion[];
}

interface StreamNode {
  type: 'CHECKIN' | 'ICEBREAKER' | 'SHAKE' | 'LOTTERY' | 'MATCH' | 'ANNOUNCE' | 'IDLE' | 'END';
  config: any;            // 环节配置
  started_at?: number;    // 开始时间
  ended_at?: number;      // 结束时间
  metrics?: {             // 环节结束后的指标
    participation_rate: number;   // 参与率
    avg_dwell_time: number;       // 平均停留时长
    sentiment: number;            // 情感倾向
  };
}

interface ActivitySuggestion {
  type: string;            // 建议的环节类型
  reason: string;          // 自然语言理由："签到已 5 分钟，建议破冰暖场"
  one_tap_action: any;     // 一键执行的 payload
  confidence: number;      // 0-1 置信度
}
```

#### 3.1.3 状态流转 + 体验流的并存关系

| 数据 | 存储 | 用途 | 读写频率 |
|---|---|---|---|
| `current_state` (旧) | Redis (string) | 状态机校验、防非法跳转 | 高（每次 WS） |
| `experience_stream` (新) | Redis (hash) + MySQL (JSON) | UI 渲染、AI 建议、Timeline | 中（每次切环节） |

**演进路径**：v2.0 保留 `current_state` 作为底层鉴权状态，同时**新增** `experience_stream` 作为 UI 渲染层。后续版本可逐步将状态机迁移至体验流驱动。

#### 3.1.4 阶段流转图（v2.0 视角）

```
[体验开始]
   ↓
IDLE (等待主持人) ─┐
   ↓              │
CHECKIN (签到中)  │  ← history 自动追加 metrics
   ↓              │
ICEBREAKER (破冰) │
   ↓              │  ← queue 动态重排
SHAKE (摇一摇)    │     AI 持续给出 suggestions
   ↓              │
LOTTERY (抽奖)    │
   ↓              │
MATCH (匹配)      │
   ↓              │
END (结束 + 成就卡)┘
```

### 3.2 晚入场状态同步机制 (Late-Joiner Sync)
*   **痛点**：用户在抽奖进行中才扫码入场，或者大屏中途刷新，此时如果不做状态同步，两端画面会错乱。
*   **开发方案**：任何一端（大屏或手机）在建立 WebSocket 连接或通过 HTTP 短轮询获取数据时，第一步**必须且仅能**调用 `GET /api/event/{event_id}/current_state` 接口。获取到当前状态（例如正在 `STATUS_GAME_SHAKE`）后，客户端强制跳过前面的签到页面，直接渲染摇一摇手柄。

## 4. 【新增开发视角】核心通信协议与高并发处理 (Communication & Concurrency)

### 4.1 WebSocket 核心事件字典 (Event Dictionary)
为了保证稳定输出，前后端必须严格按照以下事件名进行 Pub/Sub 通信：
*   **`HOST_CHANGE_SCENE` (Client -> Server)**：主持人下发切屏指令，Payload 包含 `target_state`。
*   **`SCENE_UPDATED` (Server -> All Clients)**：服务端广播状态变更。大屏和所有用户手机收到后立刻切换 UI。
*   **`USER_CHECKED_IN` (Server -> Big Screen)**：服务端通知大屏有新用户签到，大屏渲染“暗星”飞入。
*   **`USER_SHAKE_ACTION` (User -> Server)**：用户摇动手机（节流：每 500ms 发送一次，不要每次摇动都发，防止压垮服务器）。
*   **`SHAKE_LEADERBOARD_TICK` (Server -> Big Screen)**：服务端每 500ms 将 Redis 中聚合的摇一摇排行榜下发给大屏渲染。
*   **`LOTTERY_WINNER_ANNOUNCE` (Server -> All Clients)**：公布中奖名单。中奖用户的手机触发震动特效。

### 4.2 抽奖防超卖与幂等性保障 (Idempotency Guarantee)
*   **痛点**：如果主持人因为网络卡顿连点了两下“抽取”，或者黑客通过抓包重放接口，会导致奖品被超发。
*   **开发方案**：后端必须使用 Redis Lua 脚本进行原子操作扣减奖品库存。所有关键接口（如抽奖、签到、发放积分）必须带上 `request_id` 或基于 `user_id + action` 做**幂等性校验**。

## 5. 【新增开发视角】异常边界场景与容灾设计 (Edge Cases & Fault Tolerance)
**（重要：线下活动“绝对不能卡死”，稳定性大于一切技术花活）**

1. **极端弱网环境（如酒店地下二层，几百人挤占基站）**：
   *   **降级策略**：Socket.io 默认开启 `transports: ['polling', 'websocket']`。如果 WebSocket 无法建立或频繁断开，系统静默降级为 HTTP Long Polling。用户完全无感知，虽然延迟会从 50ms 增加到 1s，但保证了抽奖和互动依然能跑通。
2. **主办方设备掉线或没电（主持人手机卡死）**：
   *   **降级策略**：设计 **“副场控 (Co-Host) 机制”**。主场控在开场前可授权 2-3 个核心工作人员为副场控。主场控掉线时，副场控的手机同样拥有切屏和发奖权限。
3. ~~**现场大屏电脑性能极差（无独立显卡的老旧 PC）**~~
   *   **v3.0 移除**：设备基线提升到 8GB 内存 + i8 处理器，不再做 2D 降级。若设备无法启动 WebGL 3D，提示用户更换设备（舞台效果是大屏端的核心竞争力）。
4. **用户恶意刷票或作弊（使用模拟器摇一摇）**：
   *   **防刷策略**：前端节流控制；后端对单用户每秒最大的 `USER_SHAKE_ACTION` 数值设定阈值（例如人类极限是 10 次/秒），超过该数值的请求直接丢弃并标记异常。

## 8. 【v2.0 核心】体验驱动重构 (UX-Driven Refactor)

> 本章是 v2.0 的**核心新增内容**。基于"教程、引导只是止痛药，UX 才是治本"的理念，本章提出**舞台模型 (Stage Model)**、**指挥家视图 (Conductor)**、**智能主持人助手 (Host Assistant)** 三大架构升级，从根本上解决"用户不知道下一步干嘛"的问题。

### 8.1 核心思想：三个根本性重构

#### 8.1.1 从"Page-Per-Scene"到"Stage Model"

**旧**：每场景一个页面，靠 WS 推送跳转
```
用户进入 → checkin.vue →  WS 推 →  shake.vue
          → WS 推 →  lottery.vue → WS 推 →  match.vue
          → WS 推 →  achievement.vue → 离开
问题：每次跳转 = 一次认知重启 = 一次流失风险
```

**新**：单一 Live 容器 + 多 Overlay 演员
```
┌─────────────────────────────────────────────────┐
│  Header  [Event]    [在场 23 人]    [我 ⋯]      │  ← 永远在
├─────────────────────────────────────────────────┤
│         ✨ 当前环节：自由交流 ✨                  │  ← StageStatus
│                                                 │
│      [MainStage 动态变换：                       │  ← 单一容器内的演员
│       签到/破冰/摇一摇/抽奖/匹配/结束]           │
│                                                 │
├─────────────────────────────────────────────────┤
│  [我:🌟]  [我已就绪]   [⏭ 下一环节 3:00]       │  ← ContextBar 永远在
└─────────────────────────────────────────────────┘
       ↗ 右上角 Drawer：成就 / 聊天 / 社交池
优势：用户从未"换页"，所有变化都是舞台内的"演绎"
```

#### 8.1.2 从"场控台"到"Conductor 指挥家视图"（v3.1 单列深度重构）

**v1.x 旧**：10 个场景按钮 + 5 个表单页 = 飞机驾驶舱
**v2.0 旧**（横排布局）：左 30% 大屏 iframe/WebView 预览 + 右 70% 控制面板
  - ❌ 问题 1：iframe URL 跨域/端口不一致（H5 端 miniapp `:5174` vs 屏幕 `:5173`）
  - ❌ 问题 2：微信小程序端 `web-view` 必须白名单，否则空白
  - ❌ 问题 3：iframe 是独立 window，WS 独立，3D 跑两遍
  - ❌ 问题 4：横排 30/70 比例下，预览框被控件侧内容撑到 500rpx+，浪费空间
  - ❌ 问题 5：用户反馈"很长、没有实时预览"——iframe 经常不更新

**v3.1 新**（单列布局，手机优先）：
- **顶部 Header**（sticky, ~56rpx）：logo + 活动名 + 连接状态 + 切换/结束（圆形图标按钮）
- **Hero 卡**（mirror + stats 三合一, ~240rpx）：
  - 左侧 160rpx **CSS 镜像环**（替代 iframe）——双层 ring 呼吸 + 中心 icon + 渐变背景，
    共享屏幕同款 `currentGradient`，切场景瞬时变色、零延迟
  - 右侧 环节名 + 3 项数据（到场 / 互动 / 下一）
- **智能建议**（变色调边框卡, ~80rpx）：💡 标题 + 原因（一行解释）
- **主操作**（永远 1 个大按钮, 100rpx 高，100% 宽）：当前环节唯一正确的下一步
- **次要操作**（跳过此环节, 64rpx 小按钮）：不再像 v2.0 那样堆 2-3 个并排按钮
- **更多建议**（多于 1 条时折叠展开）：可点开看
- **底部 Timeline**（sticky, ~100rpx）：横向滚动，可点切换

优势：主持人一眼看到"现在是什么 / 多少人 / 下一步该做什么"，无任何视觉噪音。

#### 8.1.3 从"手动决策"到"Host Assistant 智能助手"

**旧**：主持人要记住 5+ 种环节切换逻辑
**新**：后端 `HostAssistantService` 持续分析活动数据，给出"下一步建议"：
- "签到已 5 分钟，建议破冰暖场" + [一键发起]
- "气氛正好，灵魂匹配拉满体验" + [一键发起]

### 8.5 体验流（Experience Stream）后端实现

#### 8.5.1 数据存储

